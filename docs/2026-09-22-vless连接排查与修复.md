# VLESS 等节点链接连不上 — 排查与修复记录（2026-09-22）

## 1. 问题

App 内置 sing-box 代理（Nagram XF 多协议代理页）中，导入的 `vless://` 等节点链接
"连接不上"。要求：分析原因、修复、并在有内核更新时更新内核优化连接稳定性。

## 2. 排查范围（代码审阅）

- 引擎层：`LibboxEngine.kt`（libbox CommandServer 生命周期）
- 运行时：`ProxyEngineClient.kt`、`SingBoxEngineService.kt`、`EngineProtocol.kt`、
  `SharedConfig.java`（`SingProxy` / `setCurrentProxy` / `setProxyEnable` /
  `loadProxyList` / `recoverExternalProxyIfNeeded` / `applySingProxyEndpoint`）
- 解析层：`VlessConfig.kt`（vless:// → sing-box JSON）、`ProxyParse.kt`、
  `ProxyLinkParser.kt`、`SubscriptionHelper.kt`
- 接线层：`ProxyListActivity.java`、`ProxyUtil.kt`（网络回调）、
  `ConnectionsManager.java`（ws 哨兵翻译）、`AndroidManifest.xml`（`:singbox` 进程）

配置生成链路（mixed 入站 + 单一 outbound + `route.final=proxy`）本身对主流节点
（tls+ws、reality、grpc）是 schema 正确的，问题集中在**状态持久化**与**链接解析边界**。

## 3. 根因（按置信度排序）

### 根因 A（高置信，必然导致"连不上"）：冷启动残留本地端点被物化成原生 SOCKS 行

`loadProxyList()` 末尾（`SharedConfig.java`）：

```java
if (currentProxy == null && !TextUtils.isEmpty(proxyAddress) && proxyPort > 0) {
    ProxyInfo info = currentProxy = new ProxyInfo(proxyAddress, ...); // 直接物化
    proxyList.add(0, info);
}
```

sing-box 节点启用后会把 `proxy_ip=127.0.0.1`、`proxy_port=<运行时端口>` 持久化。
一旦重启后 `current_proxy` 哈希与列表不匹配（如升级迁移、节点链接被编辑、或首次
装载顺序差异），上面的兜底会把 `127.0.0.1:端口` **物化成一条原生 SOCKS5 代理行**
并设为当前代理：

- 它不是 `SingProxy`，走 `applyNativeProxy` → Telegram 被指向一个**没有引擎在监听**的端口；
- 用户看到的界面是"代理已启用"，但**所有连接都失败**，且重启/编辑节点都复现。

### 根因 B（高置信）：网络回调自动选中/启用内置 ws 行（死后端）

`ProxyUtil.registerNetworkCallback().onAvailable`：

```kotlin
if (currentProxy == null && proxyList.isNotEmpty()) setCurrentProxy(proxyList[0]) // = 内置 ws 行
if ((isProxyEnabled() && vpn) || (!isProxyEnabled() && !vpn)) setProxyEnable(!vpn)  // 无 VPN 即自动启用
```

`proxyList[0]` 恒为内置 ws 行（`ws.nagramxf`，其上游域名设计文档已声明 NXDOMAIN）。
首次安装/切换网络且未手动选择节点时，回调会**自动选中并启用死代理**，表现为
"打开即连不上"；`onAvailable` 每次网络变化都会触发，覆盖用户后续手动选择前的窗口期。

### 根因 C（中高置信）：VLESS 链接解析边界导致引擎启动失败或握手失败

`VlessConfig.parseVless` 的四个缺口：

1. **`sni` 缺 `host` 回退**：大量机场只给 `host=`（ws Host）不给 `sni=`。
   此时 `server_name` 缺失 → sing-box 用 `server` 地址做 SNI → TLS 被路由到错误
   vhost（CDN 类节点必挂）。
2. **`flow` 未白名单**：旧式 `flow=xtls-rprx-vision-udp443` 等值直接透传 →
   sing-box 启动期拒绝整份配置 → 该节点"完全连不上"。
3. **`reality` 缺 `pbk` 仍发 reality 块**：空 `public_key` 无法握手。
4. **`type=h2` / `type=http` 未映射**：这两个传输类型会掉进默认分支（无 transport），
   与服务器实际协议不符。

## 4. 修复内容

| 文件 | 修改 |
|---|---|
| `SharedConfig.java` | `loadProxyList` 不再把 `127.0.0.1:port` 物化成原生 SOCKS 行：先按存活端口匹配已有 `SingProxy`；无匹配则清除残留端点（下次启用引擎绑定新端口）。新增 `isLocalhostAddress`。 |
| `ProxyUtil.kt` | `onAvailable` 只响应 VPN 切换（VPN 出现→停代理；VPN 消失→若当前代理非 ws 行则恢复）；**删除** `currentProxy==null` 时自动选中 `proxyList[0]` 与无条件自动启用。 |
| `VlessConfig.kt` | `uuid` 做 URL 解码；`flow` 白名单（仅 `xtls-rprx-vision`）；`sni` 回退 `host`；`reality` 仅在有 `pbk` 时下发；补 `h2`→http、`http`→httpupgrade 传输映射。 |
| `LibboxEngine.kt` | 内核升级配套：`PlatformStub` 按 v1.14.1 接口实现 27 个方法（新增 cancelNotification / start+closeNeighborMonitor / registerMyInterface / usePlatformShell / checkPlatformShell / openShellSession / lookupUser / lookupSFTPServer / readSystemSSHHostKey / tailscaleHostname / usePlatformBridge / createBridge；移除已不在接口中的 systemCertificates）；`ServerHandler` 补 triggerNativeCrash / connectSSHAgent。 |
| `.github/workflows/build_arm64.yml` | `LIBBOX_VERSION: v1.13.21 → v1.14.1`（CI 拉取并缓存新 AAR）。 |
| `docs/proxy-redesign.md` | 同步内核版本与 PlatformInterface 桩说明。 |

## 5. 内核更新评估（sing-box / libbox）

- 现状：`v1.13.21` 已是 **1.13.x 线最后一版**（proother/sing-box-lib 2026-08-30 发布），
  该线内没有更高版本可升。
- 更新目标：**v1.14.1**（sing-box 当前稳定版，2026-09-14 发布；
  proother `libbox-android.aar.zip` 2026-09-15 已出，CI 可直接拉取）。
- 兼容性核对（sing-box 官方 migration / changelog）：
  - 1.14 破坏性变更集中在 **DNS 配置 / inline ACME / TUN / macOS 客户端**；
    本项目生成的配置（`mixed` 入站 + vless/vmess/trojan/ss/hysteria/hysteria2/tuic
    出站 + `route.final`）**无 schema 破坏**。
  - 变化点：`PlatformInterface` 由 15 个方法扩到 **27 个**（新增 shell / bridge /
    neighbor-monitor / tailscale 等回调）→ 已按 v1.14.1 接口补全 `PlatformStub`；
    `CommandServerHandler` 增加 `triggerNativeCrash` / `connectSSHAgent` → 已补。
  - `CommandServer.start/close/closeService/startOrReloadService(config, OverrideOptions)`
    签名未变，引擎调用链无需改动。
- 收益：落在稳定线的最新修复（1.13→1.14 含多轮 TLS/传输/稳定性修复），
  并解除"旧桩接口"对未来升级的钳制。

## 6. 验证方法与剩余风险

- **本机未做编译验证**：当前机器无 JDK/SDK，且 GitHub 不可达，未能本地拉取
  v1.14.1 AAR 做 javap 级核验。`PlatformStub` 依据 pkg.go.dev 上 v1.14.1 的
  `libbox.PlatformInterface` 逐方法实现；gomobile 生成的 Kotlin 绑定对 Go `string`
  采用非空标注（与既有 15 方法桩一致）。若 CI 编译报个别签名不匹配（空值/参数名），
  属一行级微调，以 CI 编译错误为准修正。
- **CI 是本次的验证门**：push 后 GitHub Actions 拉取 v1.14.1 AAR 编译；编译通过 +
  真机测试通过才算闭环。
- **真机验证清单**：
  1. 重启 App（不手动选节点）→ 不应自动启用任何代理；
  2. 冷启动后启用 VLESS 节点 → 应连上；重启 App → 应仍连上（无残留 127.0.0.1 行）；
  3. 切换 WiFi/移动网络 → 代理状态不应被异常改写；
  4. 带 `host` 无 `sni` 的 ws+tls 节点、reality 节点、`type=h2` 节点各测一条；
  5. 关闭代理 → VPN 开启 → 代理应被停用，VPN 关闭后恢复。
- 未改动项（有意保留）：引擎启动失败仍只写日志、UI 不回显具体错误（现状设计）；
  节点 ping 检测仍跳过 sing 节点。如需在节点行上展示引擎错误可另行排期。

## 7. 结论

"VLESS 等链接连不上"在本代码库内的可证根因是**状态持久化把本地引擎端点物化成
死 SOCKS 行**、**网络回调自动启用死 ws 行**，以及**部分链接参数导致引擎配置被拒/
握手错 vhost**；本次已全部修复。内核已从 1.13 线末版升级到当前稳定版 v1.14.1，
并完成 PlatformInterface 桩迁移。剩余不确定性仅在编译期签名微调，由 CI 闭环。
