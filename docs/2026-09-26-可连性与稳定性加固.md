# 2026-09-26 代理「可连接 + 连接稳定」链路加固

> 目标：以「链接可连」与「连接稳定」为唯一判据，审计并优化整条代理链路中影响这两点的代码。
> 范围：sing-box 节点引擎（`:singbox`）、内置 ws 代理（tcp2ws relay）、连通性探测与轮询、
> 代理切换与恢复。**不改动任何节点链接格式或持久化 schema。**

---

## 一、结论摘要

配置层（`VlessConfig.buildConfig`）经官方文档逐项核实**无致命缺陷**，问题全部集中在**应用层**。
本轮定位并修复 5 个直接威胁「可连 / 稳定」的缺陷，按影响排序：

| # | 缺陷 | 主要损害 | 文件 |
|---|---|---|---|
| 1 | 空转的探测批次仍会停掉引擎，连带清空恢复锚点 | 可连 + 稳定 | `ProxyConnectivityHelper.kt` |
| 2 | tcp2ws relay 绑定失败被后台线程吞掉，状态位却已置为「已启动」 | 可连（永久不可用） | `libs/tcp2ws/tcp2wsServer.java`、`WebSocketHelper.kt` |
| 3 | 节点 A → 节点 B 切换时先 `STOP` 再 `START`，中间本地端口无人监听 | 稳定（每次切换必断） | `SharedConfig.java` |
| 4 | 连续 2 次探测失败即把**在用**代理判为不可用 | 稳定（误判 → 误切换） | `ProxyPingController.java` |
| 5 | 引擎恢复只有「绑定回调 / 前后台切换」两条路径，5 轮耗尽后永久放弃 | 可连（不自愈） | `ProxyPingController.java` |

## 二、配置层核实（不改代码，仅确认现状正确）

依据 sing-box 官方文档逐项核对，**排除**了三个原本被怀疑会致命的问题：

1. **`dns.servers[].type = "udp"`（1.12+ 新格式）默认走 direct dialer，不经过 `route.final`。**
   官方原文：*"the new one uses dialer just like outbound, which is equivalent to using an empty
   direct outbound by default"*。
   → 因此 `route.final = "proxy"` **不会**把引导 DNS 查询绕进代理，不存在
   「解析节点域名需先连上节点」的循环依赖。现有 DNS 注入正确。
2. **`outbound.domain_resolver` 自 1.14.0 起为必需项**（原文：*"this item will be required for
   outbound/endpoints using domain name in server address since sing-box 1.14.0"*），
   且可直接写 tag 字符串。当前实现只在 server 为域名时注入 → 正确，且对 IP 字面量零影响。
3. **`dns.strategy` 在 1.14 仍然有效**（被移除的是 `dns.independent_cache`，本项目未使用）。
   `prefer_ipv4` 用于规避陈旧 AAAA 记录导致的 IPv6 优先超时 → 保留。

其它已核实项：`domain_strategy` 在 Dial Fields 中已弃用（本项目未用）；route 规则的 `outbound`
字段替换属 1.11 变更（本项目未用规则）；`log.level/timestamp`、mixed inbound 的
`listen/listen_port` 均为现行字段。

**内核版本确认**：`.github/workflows/build_arm64.yml:37` 为 `LIBBOX_VERSION: "v1.14.1"`。
`NagramXF-复用交接提示词.md` 中「锁死 v1.13.21 / 禁止升 v1.14.0」的说法与 CI 实际不符，**文档需更正**
（`PlatformStub` 是按 v1.14.1 实现的，见 `LibboxEngine.kt` 的 NULL-RETURN 契约）。

## 三、逐项改动

### 改动 1 —— 空转批次不得触碰引擎（`ProxyConnectivityHelper.kt`）

**根因。** `testNodes()` 在候选全部处于新鲜期时 `added` 为空，但仍无条件执行
`busy = true; scheduleProcessNext(200ms)`；`processNext()` 见队列为空立即 `drain()`，
而 `drain()` **无条件**调用 `restoreEngineState()` → `ProxyEngineClient.stop()`。

`ProxyEngineClient.stop()` 会 `lastLink = null`（恢复锚点）。而 `testNodes` 的调用方是
「任何一次列表重建」与轮换控制器，属于高频路径。后果：
- 对**刚启动、尚未回执**的节点发出一条 `stop`，把正在建立的引擎拆掉；
- 清空 `lastLink`，使后续引擎进程被杀时失去恢复依据。

**改动。** 引入 `engineTouched` 标志：仅在 `processNext()` 真正发起 `ProxyEngineClient.start()`
时置 `true`；`drain()` 与 `cancel()` 只在 `engineTouched` 为真时调用 `restoreEngineState()`。
`cancel()` 保留「本批确实启动过引擎则归还」的原语义，避免页面退出后留下孤儿引擎。

**影响。** 列表刷新、通知驱动的 `updateRows`、轮换空批次都不再产生引擎 `stop`。

### 改动 2 —— tcp2ws relay 绑定必须同步失败（`tcp2wsServer.java` + `WebSocketHelper.kt`）

**根因（隐藏最深、后果最重）。** 原实现：

```java
public synchronized void start(int listenPort) {
    ...
    this.port = listenPort;
    new Thread(new ServerProcess()).start();   // 异步！立即返回
}
private class ServerProcess implements Runnable {
    public void run() {
        try { handleClients(port); }            // new ServerSocket(port) 在这里
        catch (IOException e) { Thread.currentThread().interrupt(); }  // 被吞掉
    }
}
```

端口被占用时 `new ServerSocket(port)` 抛 `IOException`，**在无人观察的后台线程里被静默吞掉**；
而 `WebSocketHelper` 已经执行 `tcp2wsStarted = true` 并缓存了 `socksPort`。
由于 `getSocksPort()` 首行是 `if (tcp2wsStarted && socksPort != -1) return socksPort`，
此后**整个进程生命周期内**所有调用方（`ConnectionsManager` 的
`init` / `setProxySettings` / `checkProxy`）都会拿到这个「已启动但无人监听」的端口
→ Telegram 指向死端口 → **内置 ws 代理永久连不上，且没有任何恢复路径**。

**改动。**
- `start()` 改为在**调用线程**完成 `new ServerSocket(port)` + `setSoTimeout`，
  绑定失败直接 `throws IOException`；成功后才起后台线程跑 accept 循环（`ServerProcess` 改持 socket）。
- accept 循环里残留的 `IOException` 不再用 `interrupt()` 吞掉，改为打印。
- `WebSocketHelper.getSocksPort(port)`：先算目标端口、再启动、**成功后才**写
  `socksPort` / `tcp2wsStarted`；失败时清空三处状态（使下一次调用重建 relay 而非复用陈旧端口），
  并按原语义回退到随机空闲端口重试一次；随机取端口逻辑抽为 `findFreePort()`。

**影响。** `tcp2wsStarted == true` 从「意图」变为「事实」；端口被占时上层能立即看到失败并换端口重试。
`socksPortIfRunning()` 的语义随之变为可信（其文档已同步更新）。

### 改动 3 —— 节点间切换交给引擎原子替换（`SharedConfig.java`）

**根因。** `setCurrentProxy()` 在 `previous instanceof SingProxy && previous != info` 时无条件
`stopProxyAsync(previous)`。而 `:singbox` 是单引擎：`handleStart` 本身就会
`stopLocked()` 再 `startOrReloadConfig`。因此「先显式停」把一次原子替换拆成了
「STOP 往返 + 引擎拆除 → START 往返 + 引擎重建」，中间窗口内 **`127.0.0.1:port` 无监听**，
Telegram 必然断连。

**改动。** 仅在 `enabled && info instanceof SingProxy`（启用状态下节点 → 节点）时跳过显式停止，
直接由 `startProxyAsync(info)` 交给服务端替换。其余全部情形（切到原生 / ws、切到 null、
**代理未启用**）保持原样停止，避免停用状态下留下无人使用的引擎。

**影响。** 节点间切换的空窗从「两次往返 + 一次完整拆除」缩短为「一次往返 + 服务端内部替换」。

### 改动 4 —— 失败判定不得误伤在用代理（`ProxyPingController.java`）

**根因。** 原逻辑「连续 2 次失败即 `available = false`」。10 s 周期下 20 s 的瞬时抖动
（Wi-Fi/蜂窝切换、弱网）即可把**正在使用的**代理判死。这不是无害的：
`ProxyListActivity.updateRows` 会按其排序规则给不可用行 `bias += 100000`（排到末尾），
`ProxyRotationController` 也会把它当作死代理。用户看到「当前代理不可用」→ 手动切换 → 亲手打断一条可用连接。
此外该写入**不发送 `proxyCheckDone`**，而列表与轮换只监听 `proxyCheckDone`
→ 内存状态与两个消费方长期不一致。

**改动。**
- 阈值 2 → 3（10 s 周期 ≈ 30 s 判定窗口）；
- 新增 `isEngineDownFor()`：节点代理且引擎未运行时，**不计入失败、不改动测量状态**
  （引擎问题是引擎问题，不是节点结论）——覆盖「探测途中引擎才死」的竞态；
- 判定为不可用时**补发 `proxyCheckDone`**，仅在状态真正发生 `true → false` 跃迁时发一次，
  消除状态不一致，同时让轮换控制器能据此启动故障转移判断。

### 改动 5 —— 引擎存活自检（`ProxyPingController.java`）

**根因。** 引擎恢复只有两条触发路径：`ProxyEngineClient` 的绑定/进程回调（`scheduleRecovery`，
**上限 5 轮**，耗尽后 `recoveryRounds` 不再重置直到引擎真正应答），以及
`SharedConfig.recoverExternalProxyIfNeeded()`（仅在回到前台时跑）。
若应用长时间停留在前台、且 5 轮恢复全部失败（例如网络当时不可用），
**节点会一直不可用直到用户切一次前后台**。

**改动。** 复用既有 10 s 心跳，每 3 拍（≈30 s）执行 `checkEngineLiveness()`：
代理已启用 + 当前代理是节点 + `!ProxyEngineClient.isEngineRunning()` 时，
经 `ProxyEngineClient.recoverEngine()` 触发一次恢复；恢复走
`SharedConfig.ensureCurrentExternalStarted()`（**从持久化状态出发，幂等**）。
以 `ENGINE_CHECK_THROTTLE_MS = 25 s` 节流，避免配置本身有问题的节点被无限重启（忙等）。

## 四、明确未实施的项（附理由）

**节点故障时无法自动切换到另一节点（功能缺口，本轮不动）。**

现状：`ProxyConnectivityHelper.canProbe()` 规定「当前代理是节点时，只允许探测该节点本身」。
这是为了防止「探测其它节点 = 停掉在服务的节点」。但由此产生两个后果：
1. 当前节点死亡时，自动选择/轮换**完全无法生效**（既测不到别的节点，也不会切换）；
2. `ProxyRotationController` 的类注释仍写着「节点候选在一次性 `:singbox_test` 引擎里测量」，
   而该测试进程已在 2026-09-23 第三轮被删除 → **注释与实现不符，需修正**。

看似最小的放开方式（仅在 `!ProxyEngineClient.isEngineRunning()` 时允许探测其它候选）**存在陷阱**：
探测候选会把引擎切到候选节点，批次结束后 `restoreEngineState()` 因
`keepRunning == true`（当前代理仍是节点）而不做任何事 → 引擎留在候选节点上，
而 Telegram 仍指向**在用节点**的端口 → 依旧不通，且此时
`isEngineRunning() == true`，改动 5 的自检也不会介入。
因此必须同时实现「批次结束时把在用节点启回来」，并与 `ProxyEngineClient` 的恢复路径
（进程死亡后 1.5 s 的 `scheduleRecovery`）互斥，否则两条启动路径会互相拆台。

**结论**：该改动面较大且需真机验证启动竞争，本轮不引入，作为下一轮的首选项。

## 七、剩余风险

1. **改动 2 修改了第三方库 `libs/tcp2ws`。** 该库仅被 `WebSocketHelper` 引用（已确认全仓唯一调用方），
   但 `start()` 新增了 `throws IOException`；Kotlin 调用方不需要声明受检异常，已置于既有
   `try/catch (Exception)` 内。若将来有 Java 调用方，需显式处理。
2. **改动 5 引入了「每 ~30 s 一次的重试」**。对配置本身被引擎拒绝的节点（`VlessConfig.buildConfig`
   返回 null 或引擎拒绝字段），会以约 30 s 的频率重复尝试并每次刷新 `available=false`。
   频率有界，但日志会周期性出现。
3. **改动 4 把判定窗口拉到 30 s**。若节点确实已死，界面标记不可用会比之前晚约 10 s。
4. **节点故障转移仍缺失**（见第四节），启用「自动选择代理」时对节点类代理的实际效果有限。
5. `ProxyRotationController` 类注释与实现不符（提到已删除的 `:singbox_test`）——本轮仅记录，建议下一轮修正。
