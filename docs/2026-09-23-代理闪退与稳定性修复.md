# 代理闪退 / 连不上 / 重复重连 — 排查与修复记录（2026-09-23 第二轮）

> 承接同日的《sing-box 连接排查与修复记录》。本轮针对用户新报的六项问题，仅在本项目
> 代码库内排查（本机无 JDK/SDK/设备，未编译、未真机，改动以 CI 编译 + 真机验证闭环）。

## 1. 问题清单

| # | 现象 |
|---|---|
| 1 | 粘贴 Sing-box 代理链接会触发闪退 |
| 2 | 代理连接稳定性差 |
| 3 | 所有代理需要支持自动选择 |
| 4 | 所有代理需要显示是否能够连接 |
| 5 | Sing-box 代理连接不上 |
| 6 | 短时间内出现多次重连代理 |

## 2. 根因（按置信度排序）

### 根因 A（高置信，问题 2/5/6 的主因）：连通性测试用的是**正在使用的那个引擎**

引擎进程 `:singbox` 内一次只跑一个节点；`SingBoxEngineService.handleStart` 对"非当前
link"一律先 `stopLocked()` 再启动新节点。上一轮已把"不能把在用节点和其它节点混批"作为
约束写进 `ProxyListActivity`，但约束本身只是**回避**，不是修复：

- 一旦需要测其它节点（轮换候选、非启用的节点行），引擎就必须先把在用节点**停掉**；
- 测试期间 Telegram 仍指向 `127.0.0.1:<原端口>`，端口上没有监听 → 连接失败、反复重连；
- 测完 `restoreEngineState()` 才把在用节点重新拉起 → 一次测试 = 一次"断连+重连"。
  死节点测试最长 20s，用户感知为"用着用着就断，然后过一会儿又连上"。

### 根因 B（高置信，问题 4/6）：可用性状态与时间基准不一致

- `ProxyPingController` 用 `System.currentTimeMillis()` 写 `availableCheckTime`，而
  `ProxyListActivity` / `ProxyConnectivityHelper` / `ProxyRotationController` 全部用
  `SystemClock.elapsedRealtime()` 判定"是否新鲜"。两者相差约 20 个数量级 → 刚测出的结果
  被判为陈旧 → **每次列表刷新都重测** → 每次都触发引擎启停（叠加根因 A）→ 反复重连。
- `available` 未持久化：每次重载列表所有行都回落为"不可用"，直到下一次探测。
- 在用节点为 sing 节点时，`checkProxyList` 直接 `continue` 跳过**其它所有** sing 节点
  （为了让在用节点不被停掉），其它行因此长期显示旧状态 / 不可用 —— 与"所有代理显示是否
  能够连接"直接冲突。

### 根因 C（高置信，问题 1）：粘贴路径存在"异常逃逸 = 进程死亡"的通道

- `ProxyUtil.importFromClipboard` 与 `VlessNodeEditActivity.fillLinkFromText` 都在**裸
  `Thread`** 里做解压/解析，线程内**没有 try/catch**。JVM 默认未捕获异常处理器会直接结束
  进程 → 任何解析期异常（超长剪贴板导致的 OOM、base64 退化输入等）都表现为"粘贴即闪退"。
- `ProxyLinkParser.parse` 只有 base64 分支包了 `runCatching`，主流程（`extractAll`、逐行
  循环、bare host）没有兜底。
- 解析工作全部在 **UI 线程**执行（`importFromClipboard` 旧实现、`fillLinkFromText`），大
  剪贴板会卡 UI。
- `ProxyListActivity` 的稳定 id 用 `proxyInfo.hashCode()`，与 -1…-11 的哨兵 id 处在同一
  取值空间，理论上可撞号（RecyclerView 稳定 id 重复会抛异常）。
- `SharedConfig.getProxyList()` 用 `while (true)` 重试，一旦并发修改导致构造失败就是**UI
  线程死循环**（ANR，用户感知同样是"闪退/卡死"）。

### 根因 D（中高置信，问题 5）：配置层导致"引擎拒绝整份配置"或"握手到错误 vhost"

| 项 | 问题 |
|---|---|
| Trojan | `TrojanBean` 无传输层字段，`buildTrojanOutbound` 只发裸 TCP；`type=ws/grpc/h2` 的 Trojan 节点**永远连不上**；且未下发 `alpn` / `insecure` |
| Trojan/VMess/Hysteria2/SS | TLS 的 `server_name` 只回退服务器地址，机场普遍只给 `host`（CDN vhost）→ 握手路由到错误 vhost |
| Shadowsocks | 直接丢弃 `plugin`（注释称 sing-box 不支持，实际 sing-box 支持 `plugin`/`plugin_opts`）→ obfs / v2ray-plugin 节点连不上 |
| VMess | `security` 原样透传；链接生成器常写 `aes-256-gcm`（SS 密码学套件）→ 引擎启动期拒绝整份配置 |
| Hysteria2 | `obfs` 原样透传；仅 `salamander` 合法，其它值使配置被拒 |
| TUIC | `congestion_control` / `udp_relay_mode` 原样透传；非法枚举值使配置被拒 |
| 密码解码 | 用 `URLDecoder` 解码 userinfo 密码，把字面量 `+` 变成空格 → 认证失败（"没有错误但连不上"） |
| `hy2://` | `ProxyTypes.scheme/kind/isSupported` 不认 `hy2://`，未归一化的别名链接被静默丢弃 |

### 根因 E（中置信，问题 4）：内置 ws 行的探测地址错误

`ConnectionsManager.setProxySettings`（仅静态方法）会把哨兵域名 `ws.nagramxf` 翻译成
`127.0.0.1:<relay端口>`，但 `checkProxy` **不做翻译**。于是 ws 行的连通性探测永远在查
`ws.nagramxf`（NXDOMAIN）→ 无论 ws 代理是否可用，该行恒显示"不可用"。

## 3. 修复内容

### 3.1 连通性测试与在用引擎彻底隔离（问题 2/4/5/6）

| 文件 | 修改 |
|---|---|
| `services/SingBoxTestEngineService.kt`（新增） | 一次性测试引擎宿主，继承 `SingBoxEngineService`，声明在**独立进程 `:singbox_test`** |
| `services/SingBoxEngineService.kt` | 类改为 `open`（供上面继承） |
| `helpers/ProxyTestEngineClient.kt`（新增） | 测试引擎极简客户端：bind → START → 回执，批末 `release()` 发 STOP 并解绑；12s 连接超时兜底，任何入口不抛异常 |
| `AndroidManifest.xml` | 新增 `SingBoxTestEngineService`（`android:process=":singbox_test"`） |
| `ApplicationLoader.isEngineProcess()` | 同时识别 `:singbox` 与 `:singbox_test`，测试进程不初始化 Telegram 全栈 |
| `helpers/ProxyConnectivityHelper.kt` | 改用 `ProxyTestEngineClient`；**删除** `restoreEngineState()`（不再需要在用节点的停/起）；批末释放测试引擎；不得把测试端口写回在用节点；新增 `cancel()` |

收益：测速/重测 ping/轮换候选检测**不再触碰在用节点**——连接不再被打断；每一行（含在用节点
之外的节点）都能拿到真实可用性；坏节点导致 libbox 原生崩溃只死掉一次性进程。

### 3.2 状态显示与时间基准（问题 4/6）

| 文件 | 修改 |
|---|---|
| `SharedConfig.ProxyInfo.toJsonInternal` / `SingProxy.toJsonInternal` / `proxyFromJson` | 持久化并恢复 `available`（列表重载不再整排回落为"不可用"） |
| `ProxyPingController` | 时间戳改用 `SystemClock.elapsedRealtime()`；连续 2 次失败才判不可用；节点引擎尚未应答时直接跳过（不误判）；ws 行改测本地 relay 端口 |
| `ProxyListActivity.checkProxyList` | 统一时间基准与新鲜度（可用 60s / 不可用 15s）；**不再跳过**正在使用的 sing 节点之外的其它节点；ws 行走本地 relay 探测（`WebSocketHelper.socksPortIfRunning()`，不启动 relay） |
| `ProxyListActivity.TextDetailProxyCell.updateStatus` | 当前代理"未连接且已被判定不可用"时显示红色"不可用"，不再永远停在"连接中" |
| `helpers/WebSocketHelper.kt` | 新增 `socksPortIfRunning()`（只读，不会启动 relay） |

### 3.3 粘贴路径防闪退（问题 1）

| 文件 | 修改 |
|---|---|
| `helpers/ProxyLinkParser.kt` | `parse()` 整体 try/catch（内部实现移入 `parseInternal`）；主流程逐段 `runCatching`；输入上限 2,000,000 字符 |
| `utils/ProxyUtil.kt` | `importFromClipboard` 全部搬到工作线程且线程内有 try/catch；新增 `parseLinks()` 安全解析入口；`applyImport` 全包 try/catch |
| `settings/VlessNodeEditActivity.java` | 订阅下载线程内补 try/catch（异常不再逃逸出裸线程）；`applyParsedLinks` 全包 try/catch；解析统一走 `ProxyUtil.parseLinks` |
| `SharedConfig.createNodeProxy` | 全包 try/catch，畸形链接返回 null（调用方提示"未找到可用链接"） |
| `ProxyListActivity.getItemId` | 代理行稳定 id 移到正数区间，与负哨兵 id 不可能撞号 |
| `SharedConfig.getProxyList` | `while (true)` 改为最多 5 次重试后返回空表，消除 UI 线程死循环（ANR） |

### 3.4 连接不上的配置层修复（问题 5）

| 文件 | 修改 |
|---|---|
| `helpers/ProxyParse.kt` | `TrojanBean` 增加 `network/host/path/serviceName/alpn/insecure` 并解析；新增 `smartDecode()`（仅当含 `%` 才解码，保住密码里的字面量 `+`），用于 Trojan/Hysteria2/TUIC/SS 密码 |
| `helpers/VlessConfig.kt` | Trojan：补 ws/grpc/h2/httpupgrade 传输层、`alpn`、`insecure`，SNI 回退 `sni → host → address`；SS：支持 `obfs-local` / `v2ray-plugin` 插件与 `plugin_opts`；VMess `security` 白名单（非法值回退 `auto`）；Hysteria2 `obfs` 仅接受 `salamander`；TUIC `congestion_control` / `udp_relay_mode` 白名单 |
| `helpers/ProxyTypes.kt` | 支持并归一化 `hy2://` |

### 3.5 所有代理支持自动选择（问题 3）

`ProxyRotationController` 重写候选与切换路径：

- 候选覆盖**全部代理类型**：原生 Socks5/MTProto 并行探测，sing 节点交给测试引擎串行探测；
- 排除当前代理、正在检测的行，以及**内置 ws 行**（上游按设计已失效，作为故障转移目标是无效的）；
- 切换统一走 `SharedConfig.setCurrentProxy` + `setProxyEnable(true)`（原生走 `applyNativeProxy`，
  节点走引擎启停），因此每种类型都能被自动选中；
- 当前代理**已被判定不可用**时（`proxySettingsChanged` 或 `proxyCheckDone` 信号）在 1.5s 后
  立即发起一轮选择，不必等"连接中"超时；原有超时轮换逻辑保留；
- 决策只采用 3 分钟内测得的可用结果，避免用陈旧 ping 切到已死代理。

### 3.6 重连抑制（问题 6）

| 文件 | 修改 |
|---|---|
| `SharedConfig.applySingProxyEndpoint` | 端口未变不再重复 `saveProxyList()`；偏好一致时不再重复写；端点仍然**每次启动都下发一次**（原生层同值不会重连），保证"刚启用代理"时不会残留下发缺失 |
| `helpers/ProxyEngineClient.kt` | 状态探测超时 2s → 3.5s（libbox 启停会阻塞引擎线程，过低会误判"未运行"并触发无谓重启） |
| `SharedConfig.startProxyAsync` | 启动失败时把节点标记为不可用并广播 `proxyCheckDone`，让行显示"不可用"并给自动选择提供信号 |
| `ProxyListActivity` | 不再对当前节点做 force 重测（此前每次进入列表页/状态刷新都会强制重测 → 引擎被反复触碰） |

## 4. 验证方法（本机未编译，需 CI + 真机闭环）

- **CI 门槛**：push 后 arm64-v8a Release 工作流编译通过（本轮新增 2 个 Kotlin 文件
  `SingBoxTestEngineService.kt` / `ProxyTestEngineClient.kt`，其余为既有文件修改，另加
  manifest 1 条 `<service>`）。
- **真机清单**：
  1. 粘贴 vless/vmess/trojan/ss/hysteria2 链接（含超长订阅体、纯 base64 体、畸形串）→ 不闪退，
     失败时提示"未找到可用链接"；
  2. 启用某节点 → 打开代理列表页 → 当前节点**不断连**，其余节点行逐个给出可用/不可用；
  3. 点"重测 ping" → 连接不断，所有行刷新；
  4. 看 `:singbox_test` 进程在测速期间存在、测速结束后可被回收；`:singbox` 全程只有一个节点；
  5. trojan+ws / ss+obfs / ss+v2ray-plugin / vmess(CDN, 仅 host) / hy2 各测一条；
  6. 断网或选一个死节点 → 若开启"使用代理轮换"，1.5s 后自动切到可用代理；未开启则行显示红色
     "不可用"；
  7. 观察 5 分钟内重连次数（`didUpdateConnectionState` 日志）应显著下降。
- **剩余风险**：
  - 两个引擎进程（`:singbox` / `:singbox_test`）同时运行 libbox，二者共享 `filesDir` 作为
    libbox base/working path。当前配置只使用 mixed 入站 + 单一 outbound，不使用 working path
    的缓存能力，理论无冲突；若真机出现异常，退回"仅当代理未启用时测试其它节点"的保守策略。
  - 测试进程首包需冷启动进程（数十~数百 ms），已由 12s 连接超时 + 15s 单节点超时覆盖。
  - 问题 1 的修复是"全链路异常兜底 + 消除裸线程异常逃逸 + 输入上限"，若真机仍能复现闪退，
    请提供 logcat 堆栈（tag：`ProxyTestEngine`/`SingBoxEngine`/`ProxyEngineClient`）以定位到行。
