## 一、结论

**中继、路由表、Cloudflare 部署三者都是干净的；问题出在设备侧网络路径被成批重置。**

三条互相独立的证据把责任从中继上摘掉：

1. 日志里**一次拒绝都没有**：`no ws upstream mapped` / `refusing the tunnel` /
   `socks request failed` / `relay failed to start` 全部为 **0** 次。把日志中出现过的
   **全部 5 个目标地址**按 `Socks4Impl#getCdn()` 的真实算法重放，**5/5 命中、0 拒绝**。
2. **服务端实测稳定**：5 个子域 `Sec-WebSocket-Protocol: binary` 握手全部 **101**；
   从本机并发开 **16 路**空闲 WebSocket（5 个子域轮转，同一出口 IP），
   **全部存活满 76 s 无任何服务端关闭**。证书 SAN = `ljili.dpdns.org` / `*.ljili.dpdns.org`，
   5 个子域校验全部通过。
3. **中继侧没有任何"全局拆除"路径**：`ProxyHandler` 的 `close()` 只作用于自己的 handler；
   唯一的静态状态是映射表与 `inactiveWs`（后者从未被写入）。`ProxyHealthController`
   无定时器且本次日志中一次都没触发，`ProxyRotationController` 也从未运行
   （日志中无 `checkProxy` / `proxy health:` / 轮换相关行）。

而故障本体是可量化、可复现的**批量中断**：

| 指标 | 实测 |
|---|---|
| 客户端侧并发连接数 | 峰值 20，稳态 13–16 |
| 链路级批量中断 | **7 次**：19:50:38.19、19:50:47.28、19:51:13.09、19:51:32.22、19:51:52.26、19:52:25.50、19:52:30.56 |
| 单次中断规模 | 5–12 条隧道在 **30 ms 内**同时报错（跨 dc1/dc2/dc4/dc5 全部子域） |
| 中断间隔 | 5.1 / 9.1 / 19.1 / 20.0 / 33.2 s（**不规则**） |
| 客户端断开原因 | reason 1（传输层错误）**55**、reason 2（握手超时）22、reason 0（正常挂起）21 |
| reason 1 断开前的入向空闲 | 中位 **2.0 s**、最小 **0.0 s**，多数落在 0.12–0.3 s |
| 用户可见表现 | 每次中断后 UI 在 **1.7–2.5 s** 内切到 `ConnectingToProxy` 再回到 `Connected` |

**reason 1 断开时入向空闲只有 0.1–0.3 s**，这一条直接否掉了"空闲被某处超时回收"的解释：
隧道是在**有流量在飞**的瞬间被硬打断的。

## 二、证据链

### 2.1 症状的精确形态：不是"连不上"，是"每 20 秒断一次"

`LaunchActivity: switch to state N` 就是 tgnet 的连接状态读数
（`ConnectionsManager`：1=Connecting、2=WaitingForNetwork、3=Connected、
4=**ConnectingToProxy**、5=Updating）。会话 B 的完整序列：

```
19:51:12.504 state 3 (Connected)
19:51:13.745 state 4 (ConnectingToProxy)   ← 中断 19:51:13.09
19:51:17.312 state 5 (Updating)
19:51:18.150 state 3
19:51:32.263 state 4                        ← 中断 19:51:32.22
19:51:34.756 state 3
19:51:43.000 state 4
19:51:44.695 state 3
19:51:52.307 state 4                        ← 中断 19:51:52.26
19:51:54.345 state 3
19:52:25.509 state 4                        ← 中断 19:52:25.50
19:52:27.518 state 3
19:52:30.608 state 4                        ← 中断 19:52:30.56
19:52:32.347 state 3
```

**每一次批量中断都对应一次 `ConnectingToProxy`**，每次约 2 秒。这不是"一直连不上"，
是"反复闪断"——用户看到的是转圈 2 秒、消息列表刷不出来。

### 2.2 故障链的时序（以 19:51:32 为例）

```
19:51:31.979  隧道正常收发（dc5 type 1 收到 184 字节报文、回 msgs_ack）
19:51:32.122  隧道正常收发（dc5 type 2 收到 120 字节）
19:51:32.221  E tcp2ws: ws error server=vesta … WebSocketException:
              An I/O error occurred while a frame was being read …
              Caused by: java.net.SocketException: Software caused connection abort
19:51:32.223  E tcp2ws: ws error server=flora … Flushing frames failed: Broken pipe
19:51:32.225  error: socket event has EPOLLRDHUP      ← 中继关掉了客户端 socket
19:51:32.226  connection(…, dc4, type 64) disconnected with reason 1
19:51:33.6→34.3  5 条隧道重新拨号成功
```

`ECONNABORTED`（读）+ `EPIPE`（写）同时出现在**所有**上游 socket 上，而同一进程的
**入向（客户端）数据在同一毫秒仍在正常解析**——所以不是进程卡死、不是 GC、
不是 CPU 节流（忙碌轮询在上一轮已改成 30 s 阻塞读）。

### 2.3 不是"连接数太多撞上限"

用 tgnet 日志逐连接配对（`connected via proxy` / `disconnected with reason`）重建的
客户端侧并发数：

| 中断时刻 | 当时存活连接数 |
|---|---|
| 19:50:38.19 | 7 |
| 19:50:47.28 | 7 |
| 19:51:13.09 | 16 |
| 19:51:32.22 | 14 |
| 19:51:52.26 | 13 |
| 19:52:25.50 | 14 |
| 19:52:30.56 | 13 |

并发 **7** 时和并发 **16** 时一样会整批中断，且并发曲线在 13–14 附近长时间平稳。
**没有任何阈值效应**，所以"中间盒按连接数限制"这条假设排除。

### 2.4 主因假设：设备侧本地地址集合被改动，内核中止了挂在旧地址上的 socket

tgnet 在初始化时枚举过一次接口（`ConnectionsManager.getIpStrategy()` 的日志），
这次枚举把设备的网络形态完整写在了日志里：

```
valid interface: name:wlan1  →  192.168.1.107
valid interface: name:wlan0  →  192.168.1.106
valid interface: name:rmnet_data0 → (仅 fe80)
valid interface: name:rmnet_data2 → 2408:8418:31f0:1020:… / 10.128.60.161
valid interface: name:rmnet_data1 → 2408:8517:3170:8e9f:…
valid interface: name:dummy0
selected ip strategy 0            ← USE_IPV4_ONLY
```

**设备同时持有 `wlan0=192.168.1.106` 与 `wlan1=192.168.1.107` —— 两个接口、同一个 /24、
两个都可用的 IPv4**（国产 ROM 的"双 WLAN / 双频并发加速"就是这种形态），
另外还有三条蜂窝接口。而应用侧**没有任何网络绑定**（全仓只搜索到 ExoPlayer 内部的
`ConnectivityManager` 用法，tgnet 也未把 socket 绑到某个 `Network`）。

在这种形态下：

* socket 只在 `connect()` 那一刻由内核选路由；此后**不绑定** `Network`；
* 当 ROM 拆掉其中一条链路（DHCP 租约回收 / 双 WLAN 聚合解除），该地址被移除；
* Linux 对"源地址已不存在的 socket"的行为是**中止**——读侧 `ECONNABORTED`，
  写侧 `EPIPE`，这正是 2.2 里看到的两个异常；
* 挂在存活地址上的新拨号**立刻成功**（实测 1.6–2.0 s 内全部重连完毕），
  与"接口整体断开"不符（那样新拨号会先失败几秒）；
* 因此表现为：**有流量时被整段打断 → 立刻换地址重连 → 过一阵再被打断**，间隔取决于
  ROM 何时再动一次链路，所以是 5–33 s 的**不规则**间隔。

这条假设解释了全部观测特征，且是**唯一**同时满足"无阈值效应 / 有流量时被打断 /
重拨立刻成功 / 跨所有 DC 同时发生 / 无应用侧事件"的机制。

**旁证**：本次日志中 3 次拨号（占 108 次的 2.8%）报
`The certificate of the peer does not match the expected hostname (<子域>)`
（19:51:13 pluto/venus、19:52:30 flora）。部署侧证书实测 SAN 为
`ljili.dpdns.org` / `*.ljili.dpdns.org`，本机 5 个子域全部校验通过，
所以这不是部署问题，而是**这条出口路径瞬时被干预过**的痕迹（握手被截断 /
被中转 / SNI 未按预期到达边缘）。按既定约定，**不因此关闭 TLS 校验**。

### 2.5 明确排除的项

| 候选 | 判据 |
|---|---|
| 路由表缺项 | 5 个目标地址重放 5/5 命中；`refusing` / `no ws upstream` / `socks request failed` 各 0 次 |
| Cloudflare / Worker / DNS / TLS 模式 | 5 子域 101；16 路并发空闲 WS 存活 76 s；证书 SAN 匹配 |
| `ProxyHealthController` 自激 | 无定时器；日志中 0 次 `proxy health:` |
| `ProxyRotationController` 轮换 | 日志中 0 次 `checkProxy`；未开启轮换 |
| `relay()` 忙轮询 | 已是 `RELAY_READ_TIMEOUT_MS = 30_000` 阻塞读 |
| 看门狗误关（100 s 无入向帧） | 日志中 0 次 `ws upstream silent` |
| 客户端重连节奏过密 | tgnet 固定 1 s 重建（`reconnectTimer->setTimeout(1000, false)`）；本次的 55 次 reason 1 是被动结果而非成因 |
| 连接数撞上限 | 并发 7 与并发 16 均整批中断，无阈值 |
| 空闲超时回收 | reason 1 断开前入向空闲中位 2.0 s、最小 0.0 s |

## 三、能从应用侧做的两件事

根因不在应用里，**应用层无法阻止内核中止 socket**。可做的只有两件：

1. **把下一次抓包的证据密度提上去**，让"是路径还是应用"一眼可判（本次判定花了一整轮
   原始日志复原，就是因为缺这三个数字）；
2. **去掉一个真实缺陷**：正常拆除被当成错误刷屏，把真信号埋掉。

### 3.1 `ProxyHandler` 现场记录（新增）

`close()` 会把客户端 socket 关掉，阻塞在 `checkClientData()` 的那次读于是抛
`SocketException: Socket closed`。原有判定写的是 `"Socket Closed"`（大写 C）与
`"socket closed"`（小写 s），而真实消息是 **"Socket closed"（大写 S、小写 c）——
两个都不匹配**。后果：**每一次正常拆除都写一段完整调用栈到 ERROR 级**。
本次日志每次批量中断产生 7–11 段这样的栈，真正的信号（谁先把谁打死）全被埋了。

现改为统一小写比较，同时新增两类记录：

* 每次上游隧道建立：`markUpstreamOpen()` 记 `upstreamOpenedAt` 并维护
  `s_liveUpstreams` 计数；
* 每次上游隧道死亡：`reportUpstreamDeath()` 输出**一行**，带三个关键数字：

```
tcp2ws: ws upstream died: vesta.ljili.dpdns.org
        (error, byUs=false, ageMs=1…, idleMs=…, sameWindow=…, live=…)
```

| 字段 | 用途 |
|---|---|
| `ageMs` | 隧道存活时长；拨号后 2 s 就死 ≠ 服务 60 s 后死 |
| `idleMs` | 死亡时入向已空闲多久；**接近 0 就排除"空闲回收"** |
| `sameWindow` | 500 ms 窗口内的第几条；>3 且跨子域 ⇒ 路径级事件 |
| `live` | 该时刻存活隧道数；判断是否有阈值效应 |
| `byUs` | `true` = 客户端 socket 先死、上游是连带；`false` = **上游自己死的**（要看的） |

同一个 handler 的死亡只报一次（`deathReported`），避免 reading/writing 两个线程各报一遍。

### 3.2 本地地址集合签名（新增）

`logAddressSignatureIfChanged()` 输出一行「本进程当前可用的非环回、非链路本地地址」，
**仅在变化时打印**：

```
tcp2ws: local address set changed (death): [rmnet_data2=10.128.60.161, wlan0=192.168.1.106, …]
```

若下一次日志里 `local address set changed` 与 `ws upstream died` **同刻出现**，
2.4 的假设即被证实；若地址集合始终不变而那些隧道照样成批死，则回到"路径被中间设备重置"，
需要换网络复核。

## 六、剩余风险

1. **2.4 的机制是推断，不是直接观测**。日志只能证明"有流量时被整批中止、地址集合当时
   未变"（tgnet 只在初始化时枚举接口）。3.2 的签名就是为把它变成直接观测而加的。
2. **证书不匹配的 3 次未闭环**。次数太少、无包捕获，目前只能记作"路径被干预的痕迹"。
   下一次若重现，应同时抓 `local address set` 与拨号失败的完整原因串。
3. **`byUs` 的语义依赖 `closed` 标志的时序**：`onError`/`onDisconnected` 均在本 handler
   自己调用 `close()` 之前读 `closed`，因此能区分"上游先死"与"我们主动拆"。若将来把
   `close()` 提前到这两个回调开头，该字段会整体退化为 `true`，失去区分能力。
4. **`s_liveUpstreams` 是估算值**，只用于看趋势与阈值效应，不作为精确计数引用。
5. 本次未改动路由表——重放已证明它 5/5 正确，没有可加的项。
