# sing-box 引擎原生崩溃：定位与修复（2026-09-24）

> 输入：用户提供的真机日志包（`logs.zip`，含 logcat 主日志 + 引擎进程日志）。
> 本轮**首次拿到崩溃栈**，此前三轮的猜测全部被推翻/收敛到同一条根因。

---

## 一、结论（先行）

**唯一的根因是 `PlatformStub.findConnectionOwner()` 返回 `null`。**

sing-box 的 libbox 在 Go 侧对这个返回值**不做空指针检查**，Java 的 `null` 传到 Go 就是一个 nil 指针，紧接着取字段即 SIGSEGV → Go runtime `abort()` → SIGABRT → **引擎进程被杀死**。而 sing-box 对**每一条本地连接**都会做这个查询（不是只在配了进程规则时），所以：

- 引擎进程一建立、第一条探测连接进来就崩 → **节点永远"不可用"**；
- 每次崩溃都触发恢复重建 → 引擎反复重启 → **"短时间多次重连"**；
- 崩溃发生在应用自己的进程（`cn.Nagram.CF:singbox`）→ Android 判定应用崩溃并弹"应用已停止" → **用户看到的"闪退"**。

一个 bug 解释了全部四个现象。修复为 1 处方法实现 + 1 处同类隐患。

### 4. AAR 实证（不是推测）

从 CI 实际使用的 `proother/sing-box-lib` release `v1.14.1` 下载 `libbox.aar`，
解析 `classes.jar` 的类文件，确认可用的构造与 setter：


## 三、改动

单文件：`TMessagesProj/src/main/java/tw/nekomimi/nekogram/helpers/LibboxEngine.kt`

| # | 位置 | 改动 | 性质 |
|---|---|---|---|
| 1 | `PlatformStub.findConnectionOwner` | `null` → 非空 `ConnectionOwner`（`userId=-1`、`userName=""`、`processPath=""`、`androidPackageNames=空 StringIterator`） | **修复根因** |
| 2 | `PlatformStub.getInterfaces` | `null` → `EmptyInterfaceIterator` | **同类隐患**：libbox 用 `iteratorToArray(...)` 直接迭代，`null` 会以完全相同的方式 panic |
| 3 | 新增 `EmptyStringIterator` / `EmptyInterfaceIterator` | 两个私有空实现 | 支撑 1、2 |
| 4 | `PlatformStub` 类注释 | 写明"绝不返回 null"的契约与上游行号 | 防止回归 |
| 5 | `useProcFS()` | 保持 `false`，加注释说明两条路径的关系 | 明确取舍 |

**为什么 `useProcFS()` 保持 `false`**：把它改成 `true` 也能绕开崩溃（libbox 转用
`procfs.ResolveSocketByProcSearch` 自行解析，永不回调 Java），代价是每条连接的
`/proc/net/tcp` 扫描。当前实现直接立即返回、零系统调用，且与官方安卓端一致，故取前者。
两者只能取其一，已注释说明"改它必须同时看 `findConnectionOwner`"。

**为什么答案是 `-1` 而不是真实 uid**：本项目配置没有 `process_name` 类路由规则、没有 TUN、
没有分应用代理，进程归属信息无人消费；libbox 自身把 `UserId == -1` 视为"未知"
（`route/process_cache.go` 中 `if processInfo.UserId != -1` 才记录）。返回 `-1` 语义诚实且静默。

## 四、为什么前三轮没找到

| 轮次 | 当时的判断 | 为何不够 |
|---|---|---|
| 第 1 轮 | 测速复用在用引擎 → 改独立进程 `:singbox_test` | 治了"重连"的表象，却引入第二个原生引擎进程，**放大了崩溃面** |
| 第 2 轮 | 导入会启动引擎 → 加可见性门控；补 DNS/hy2/trojan 传输层等配置缺陷 | 配置层这些缺陷是**真实存在**的（已用官方 `sing-box check` + 端到端转发验证），但与崩溃无关 |
| 第 3 轮 | 弹窗宿主存活、探测去抖、`start` 超时 | 全是健壮性加固，没触及原生层 |

根因始终在**原生进程内**，而 Java 侧的任何 try/catch 都拦不住 Go 的 `abort()`。
`ApplicationLoader` 的 `Thread.setDefaultUncaughtExceptionHandler` 也接不到 —— 那是另一个进程的 SIGABRT。
**没有崩溃栈时，"没有任何 Java 异常却闪退"这一现象本身就应该指向原生层**，这是本轮最大的方法论修正。

## 六、日志里另外发现的一个（**非**崩溃）问题

`NagramX-...txt` 中 3 次出现：

```
E/FileLog: java.lang.IndexOutOfBoundsException: setSpan (0 ... 6) ends beyond length 0
    at org.telegram.ui.Cells.DialogCell.buildLayout(DialogCell.java:1862)
```

**这不是闪退**：`DialogCell.java:1861-1866` 该语句被 `try { ... } catch (Exception e) { FileLog.e(e); }` 包住，
异常被捕获后只写了日志，进程继续（日志中其后仍正常 `present fragment`）。
它是本项目对话列表里一个既有的 span 越界缺陷（`fixNameStringLength(...)` 返回值大于字符串长度），
与代理无关，可作为独立小 bug 单独处理。

## 七、剩余风险

1. **`localDNSTransport()` 仍返回 `null`**：libbox 侧在 wrapper 层做了 nil 检查
   （`ReadWIFIState` 的写法同构），且当前配置只用 `type: "udp"` 的 DNS，未走 `type: "local"`。
   已保持原状，但若将来启用 `local` DNS 需重新评估。
2. **`lookupUser()` 返回 `null`**：libbox wrapper 里 `platformUser.Username` 无空检查，
   属同类隐患；触发条件是配置里引用用户（本配置无），`usePlatformShell()` 也已返回 false。已注释标注。
3. **引擎进程崩溃仍会弹"应用已停止"**：这是 Android 对应用进程 SIGABRT 的固有行为。
   本轮消除了可证的崩溃源；`ProxyEngineClient` 的恢复轮次另有 5 次上限，不会无限重启。
   若后续再出现原生崩溃，仍需 `adb logcat -b crash -d` 的栈。
