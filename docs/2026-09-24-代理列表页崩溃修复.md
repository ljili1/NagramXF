## 一、结论（先行）

`FATAL EXCEPTION`，直接杀死应用进程。**

## 二、机制：一次「重建中途的重入」

三个条件同时成立才会崩，缺一不可：

1. **`updateRows()` 先探测、后通知适配器。**
   `ProxyListActivity.updateRows()` 在**第 933 行**调用 `checkProxyList()`，
   而 `listAdapter.notifyDataSetChanged()` 在第 934 行 —— 顺序反了。
   即调用探测时，RecyclerView 上挂着的子视图**仍然描述上一版行布局**。

2. **`ProxyConnectivityHelper.testNodes()` 同步派发通知。**
   `testNodes()` 把入队节点标为 `checking` 后，**就地同步** post `proxyCheckDone`
   （`ProxyConnectivityHelper.kt:140`）。`NotificationCenter` 是同步分发，于是
   `ProxyListActivity.didReceivedNotification` 在 `updateRows` 的调用栈**内部**被重入。

3. **重入后的回调按 adapter position 取视图并强制转换。**
   ```java
   RecyclerListView.Holder holder = (RecyclerListView.Holder)
           listView.findViewHolderForAdapterPosition(idx + proxyStartRow);
   if (holder != null) {
       TextDetailProxyCell cell = (TextDetailProxyCell) holder.itemView;   // ← 1086
   ```
   此时 `proxyStartRow` 是**新**布局算出来的，而挂载的视图还是**旧**布局的；
   该位置在旧布局里是 `TextSettingsCell`（`VIEW_TYPE_TEXT_SETTING` 行）→ 转换失败。

**为什么是现在才炸**：第 2 条（同步派发"探测开始"通知）是前几轮为解决"导入链接即启动
引擎"引入的改动。原生代理行的探测走 `ConnectionsManager.checkProxy(...)`，回调是**异步**
的，从来不会在 `updateRows` 栈内重入；节点行改由 `testNodes` 同步派发后，这条重入路径才被打通。
换言之，**这是我自己引入的回归**，不是历史遗留缺陷。

**触发时机**：`SharedConfig.notifyProxyChanged()`（第 1749 行，`runOnUIThread` 包一层）由
`startProxyAsync` 的 onStarted/onError、以及应用切回前台时的引擎自检调用。日志显示
`16:13:57` 应用退到后台（PIP），`16:14:03` 回到前台，`16:14:05` 崩溃 —— 与"切回前台触发自检
→ 通知 → 行重建 → 崩溃"完全吻合。

## 三、改动（分层，任一层单独都能挡住这次崩溃）

| # | 文件:位置 | 改动 | 作用 |
|---|---|---|---|
| 1 | `ProxyListActivity.didReceivedNotification`（`proxyCheckDone` 分支） | 由「按 adapter position 取 holder」改为 `forAllChild` 遍历 + `instanceof` 校验 + 按 `cell.currentInfo == proxyInfo` 身份匹配 | **正面消除崩溃**：不再对视图类型做任何假设 |
| 2 | 同上，`didUpdateConnectionState` 分支 | 同样补 `instanceof` 校验 | 同类隐患，同一处崩溃模式 |
| 3 | `ProxyListActivity.updateRows` | `checkProxyList()` 移到 `notifyDataSetChanged()` **之后** | 消除"从旧适配器状态出发"的时序错误 |
| 4 | `ProxyConnectivityHelper.testNodes` | "探测开始"通知改为 `handler.post{}` 延后一个主循环轮次，并校验 `node.checking` | 消除"在调用方栈内重入"这一整类问题 |

关于改动 1 选 `forAllChild` 的依据：`RecyclerView.forAllChild` 除普通子视图外**还遍历
attached scrap 与 hidden child**（`RecyclerView.java:637-647`），而重建期间的悬挂 holder
正在 attached scrap 中，因此按身份匹配能正确刷新目标行。本文件 `proxyChangedByRotation`
分支（第 1048 行）早已使用同一写法，本次只是把漏掉的两处补齐。

## 五、关于「上一轮原生修复是否生效」：**日志无法证明**

必须明确说明这一点，避免误判：

- 日志里总共只有 **1 次** `LibboxEngine: node engine up (libbox 1.14.1)`（15:56:19.200），
  且 **12 毫秒后**就 panic 了。也就是说，**这台设备上引擎从未成功存活过一次**。
- 15:56 那批原生崩溃（7 次 panic，栈顶均为 `service.go:226` / `FindConnectionOwner`）
  说明当时运行的构建**不含** 169 的修复。旁证：崩溃栈里的行号
  （933 / 940 / 1016 / 1059 / 1086）与 `ProxyListActivity` 当前版本**逐一对齐**，
  而该文件最后被改动是 168（`433be01e6`）→ 15:56 跑的是 **168**。
- 16:09:59 之后**没有任何引擎活动**：16:14:05 的崩溃发生在 `testNodes` 派发"探测开始"通知的
  那一刻，**探测本身还没开始**，因此引擎根本没被启动。所以"16:09 之后没有原生崩溃"
  **不能**作为原生修复生效的证据。
- 结论：**169 的原生修复在真机上仍未得到验证**。要先装本轮修复，让探测能真正跑起来，
  才能观察到引擎是否存活。

同一份日志里其余内容均与本次崩溃无关：

- `DialogCell.java:1862` 的 `IndexOutOfBoundsException` 仍被 `try/catch` 吞掉（3 次），不是崩溃；
- `DnsFactory: All DoH providers failed ... 'apv3.stel.com'` 是 IPv6 DoH 探测失败，与应用崩溃无关。

## 六、剩余风险

1. `didUpdateConnectionState` 分支的 `idx + proxyStartRow` 仍是位置式查找，本次只加了类型校验
   未改成身份匹配。当前不会再崩，但若后续行类型再变化，建议一并统一为身份匹配。
2. `checkProxyList()` 内的原生 `checkProxy` 回调是异步的，不受本次重入问题影响；但
   `ProxyConnectivityHelper` 的其余 3 处 `proxyCheckDone` 派发
   （第 195/286/401 行）仍可能在各自调用栈内同步分发，已通过改动 1 变得无害。
3. 引擎原生层仍有未验证项（见第五节）。
