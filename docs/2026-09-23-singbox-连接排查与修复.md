## 1. 问题

用户报告内置 sing-box 代理（Nagram XF 多协议代理页）"连不上"。上轮修复后仍复现，
要求继续排查（仅限本项目文件夹）。

## 3. 根因（按置信度排序）

### 根因 A（高置信，必然导致"启用后断连"）：连通性测试把在用节点引擎停掉

引擎是**单实例**（`:singbox` 进程内一次只能跑一个节点）；`SingBoxEngineService.handleStart`
对"非当前 link"一律先 `stopLocked()` 再启动新节点。

`ProxyListActivity.checkProxyList()`（每次 `updateRows` → 进入代理页 / 状态刷新都会触发）
此前把**全部** sing 节点（含正在使用的 `currentProxy`）一次性交给
`ProxyConnectivityHelper.testNodes` 排队测试：

- 测完当前节点后，测试队列里的**下一个节点**会先把当前引擎 `stopLocked()` 停掉；
- 测试期间（每节点启动+探测，死节点可达 20s 超时）Telegram 仍指向
  `127.0.0.1:<旧端口>`，而端口上已没有引擎在监听 → **所有连接失败**；
- 测试全部排空后 `restoreEngineState()` 才重启当前节点，恢复前用户感知为
  "启用 singbox 代理后连不上 / 时断时续"。

触发面：进入代理列表页、代理状态刷新、手动"重测 ping"、节点切换后的刷新都会命中。

### 根因 B（高置信）：坏节点让引擎进程反复崩溃 → 恢复轮次上限失效 → 无限重启

`ProxyEngineClient.onServiceConnected` 每次绑定成功都重置 `recoveryRounds = 0`，
而恢复计数只在 `scheduleRecovery`（进程断开/绑定死亡）里递增。若某节点配置导致引擎进程
SIGABRT（libbox 为 native 代码，SIGABRT 无法被 Java catch）：

```
崩溃 → onServiceDisconnected → 恢复第 1 轮 → bind → onServiceConnected(重置=0) → 重启引擎 → 又崩 → 第 1 轮 → …
```

`MAX_RECOVERY_ROUNDS = 5` 的上限被 `onServiceConnected` 的重置彻底绕过，引擎进程无限重启、
`127.0.0.1:port` 反复无监听 → "代理一直连不上"且无任何 UI 提示。

### 根因 C（中置信）：vmess TLS 的 SNI 回退到服务器地址而非 vhost

`VlessConfig.buildVmessOutbound` 用 `bean.sni.ifBlank { bean.address }` 作为 TLS SNI。
大量机场的 vmess 链接只带 `host`（ws Host / CDN 域名）不带 `sni`，此时 SNI 取原始
服务器地址 → TLS 被路由到错误 vhost，CDN 类 vmess 节点握手必挂（vless 上轮已修同样的
`sni→host` 回退，vmess 漏掉）。

## 4. 修复内容

| 文件 | 修改 |
|---|---|
| `ProxyListActivity.java` | `checkProxyList` 拆分两个队列：`currentToCheck`（在用节点**单独**测试，force=true；引擎对同 link 幂等回 OK(port)，不打断）+ `othersToCheck`（其余节点）。**只要当前代理是已启用的 sing 节点，其余 sing 节点一律跳过测试**——不打扰正在使用的代理。 |
| `ProxyEngineClient.kt` | `onServiceConnected` **不再重置** `recoveryRounds`（连接成功≠引擎健康）；计数只在引擎真正应答（Start OK / Probe running）时清零。坏节点崩溃循环被 `MAX_RECOVERY_ROUNDS` 截断，不再无限重启。 |
| `VlessConfig.kt` | vmess TLS SNI 回退顺序改为 `sni → host → address`（对齐 vless 上轮修复）。 |

`ProxyConnectivityHelper` 上轮按队列串行测试的机制保留（轮换场景仍用它逐个探测），
调用方负责不把在用节点与其它节点混批。

## 5. 验证方法与剩余风险

- 本轮为纯代码审阅修复；本机无 JDK/SDK，未编译、未真机。修改点均为局部逻辑调整，
  建议 push 后由 CI（arm64-v8a Release）编译把关。
- **真机验证清单**：
  1. 启用 VLESS 节点 → 打开代理列表页 → 页面加载/刷新期间代理**不应断连**，当前节点行仍显示 Connected+Ping；
  2. 使用中点击"重测 ping" → 只测当前节点，其余节点行保持原状态，连接不断；
  3. 未启用代理时进入代理页 → 全部节点正常逐个测速，不残留引擎；
  4. 用一条"已失效/坏配置"的节点反复启用 → 引擎进程最多重启 5 轮后停止，不再无限循环，App 不卡死；
  5. CDN 型 vmess 节点（tls+ws、只有 host 无 sni）→ 应能握手连上。
- 未改动项（有意保留，承接上轮设计）：
  - 引擎启动失败仍只写日志、UI 不回显引擎错误；节点不可用时由用户手动换节点；
  - 轮换（proxy rotation）测试其它节点时仍会短暂停掉当前引擎——这是轮换的设计行为
    （本就为切换节点而测），完成后按轮换逻辑切换或恢复；
  - 死节点导致的 `startProxyAsync` 失败不会清空用户保存的代理状态。

## 6. 结论

"sing-box 代理连不上"在本代码库内的可证根因除上轮修复的三类外，还有**连通性测试
停掉在用节点引擎（进入代理页即断连）**、**坏节点崩溃导致引擎无限重启**与
**vmess SNI 回退错误（CDN 节点握手失败）**；本次已修复。剩余不确定性集中在编译
（CI 把关）与真机行为确认。
