# 代理「首次导入闪退 / 导入后不可用·连不上」— 排查与修复（2026-09-23 第三轮）

> 承接同日两份记录。本轮先取证（CI 结论 + 产物），再按"回归"排查用户新报的两个现象。
> 仍然只在本项目代码库内改动；本机无 JDK/SDK/设备，未编译、未真机。

## 1. 用户现象

1. Sing-box 链接**首次导入会闪退**；
2. 导入后节点显示**不可用，无法连接**。

## 2. 取证（关键前提）

- 查询 GitHub Actions：`Build arm64-v8a Release #164`（提交 `2d215d6`，即上一轮修复）
  **状态 Success**，耗时 20m42s，产物 `NagramXF-arm64-v8a-164`（71.8 MB），约 23:26 完成；
  用户在 23:54 报告。
- **结论：用户极可能测试的是上一轮修复后的构建**，因此这两个现象必须按"上一轮引入的回归"
  来定位，而不是旧问题的延续。

## 3. 根因

### 根因 A（高置信，问题 1）：导入动作会**间接启动引擎**

`SharedConfig.addProxy` → `notifyProxyChanged()` → 主线程广播 `proxySettingsChanged`。

`ProxyListActivity` 的观察者**不检查自身是否可见**：用户从代理列表页进入「添加节点」页粘贴
链接时，列表页只是 `onPause`（观察者仍在注册），于是：

```
导入保存 → proxySettingsChanged → 列表页 updateRows(true) → checkProxyList()
        → ProxyConnectivityHelper.testNodes() → 启动 :singbox 引擎
```

即"导入一个链接"会**连带启动 sing-box 引擎**（首次导入 = 该会话首次启动引擎）。引擎进程一旦
在原生层崩溃（libbox SIGABRT/SIGSEGV），系统会弹出"应用已停止"——用户看到的就是"导入即闪退"。
上一轮还把测试放进了新进程 `:singbox_test`，又叠加了一次"首次创建新进程"的风险。

### 根因 B（高置信，问题 2 的"不可用"）：基础设施失败被当成"节点不可用"

上一轮为满足"显示是否能够连接"，引入了两处"标记不可用"：

- `ProxyConnectivityHelper.applyResult(node, -1)`：**任何**失败都写 `available = false`；
- `SharedConfig.startProxyAsync.onError`：引擎报错即写 `available = false`。

但引擎**进程/绑定**层面的失败（bind 被拒、进程被杀、启动无回应、探测看门狗超时）与"节点本身
能不能用"无关。结果是引擎一次抖动就能把**健康节点**标成"不可用"——用户看到"导入后节点不可用"。

### 根因 C（高置信，问题 2 的"无法连接"，且可确证）：生成的配置**没有 DNS**，而 sing-box 1.14
要求 outbound 使用域名时必须配置解析器

`VlessConfig.buildConfig` 生成的配置只有 `log` / `inbounds` / `outbounds` / `route.final`，
**既没有 `dns` 段，也没有 `route.default_domain_resolver`**；而 `LibboxEngine.PlatformStub`
的 `localDNSTransport()` 返回 `null`（没有平台 DNS 传输）。

对照官方文档（已核实，见 sing-box Dial Fields）：

> "…so this item will be required for outbound/endpoints using domain name in server address
> since sing-box 1.14.0."
> —— `domain_resolver` / `route.default_domain_resolver`

节点链接绝大多数使用**域名**作为服务器地址（机场域名）。**没有解析器 → 服务器域名永不解析
→ 节点永远连不上**。这与"导入后节点不可用、无法连接"完全吻合，且是配置层可确证的缺陷
（与前两轮的"解析/持久化"问题无关，所以一直没被覆盖）。

### 根因 D（中置信，问题 2 的"连不上"且无反馈）：`start` 请求会**静默丢失**

`ProxyEngineClient.start` 没有超时；而 `bind()` 失败时只 `pendingSend.clear()`、**不回调**。
一旦绑定失败（或请求丢失），`onStarted` / `onError` 都不会触发 → 引擎永不启动、节点既不显示
可用也不会恢复，用户看到"一直连不上"。`ProxyEngineClient` 的 stop/probe 都有超时，唯独最关键的
start 没有。

## 4. 修复内容

| 文件 | 修改 |
|---|---|
| `services/SingBoxTestEngineService.kt`、`helpers/ProxyTestEngineClient.kt` | **删除**（放弃独立测试进程方案）。风险不对称：新增一个未经验证的原生引擎进程，一旦环境不兼容就会反复弹"已停止"窗口，而收益只是"代理启用时也能测其它节点" |
| `AndroidManifest.xml`、`ApplicationLoader.java`、`SingBoxEngineService.kt` | 同步回退（服务声明、`isEngineProcess()`、`open` 修饰） |
| `ProxyListActivity.java` | 新增 `pageVisible`（onResume/onPause）；`checkProxyList` 在页面不可见时**直接返回** → 导入不再触发引擎启动；返回列表页时再刷新 |
| `helpers/ProxyConnectivityHelper.kt` | ①`canProbe()`：代理启用且当前是节点时**只测该节点**（引擎幂等，不打断在用节点），其它节点跳过且**不改状态**；②失败分类：基础设施失败**不写** `available`（只清 `checking` + 置 `availableCheckTime=0` 触发后续重试）并进入 **30s 退避**；只有"配置被拒"或"探测失败"才标不可用；③节点间加 **350ms** 间隔（libbox 停/启缓冲）；④批末只在"无节点在用"时停引擎 |
| `helpers/ProxyEngineClient.kt` | 新增 `INFRA_ERROR_PREFIX` 与 `isInfrastructureError()`；**start 增加 15s 超时**（超时回调 + 有界恢复）；`bind()` 失败改为 `failPending()`（不再静默丢请求）；四条进程/绑定失败路径统一带基础设施前缀 |
| `SharedConfig.java` | `startProxyAsync.onError` 区分"配置被拒"（标不可用）与"引擎不可用"（**保留状态**） |
| `helpers/VlessConfig.kt` | **server 为域名时注入** `dns.servers=[{type:udp, tag:dns-direct, server:223.5.5.5, server_port:53}]` 并给 outbound 加 `domain_resolver: "dns-direct"`；**server 为 IP 字面量时完全不注入**（保持原配置不变，零风险）。DNS 取国内可达的公共解析器：8.8.8.8 / 1.1.1.1 在国内容易不可达，而解析器不可达等于节点不可拨通 |
| `res/values/strings.xml`、`values-zh-rCN/strings_naxf.xml`、`values-zh-rTW/strings_naxf.xml` | 新增 `ProxyCheckUnknown`（Not checked / 未检测 / 未檢測） |
| `ProxyListActivity.java`（UI） | 非当前行：从未测过（或探测未能运行）显示灰色"未检测"，不再一律显示红色"不可用" |
| `ProxyListActivity.java`、`ProxyPingController.java` | 原生 `checkProxy` 调用补 try/catch（刷新路径与 10s 定时任务不得抛异常崩进程） |

## 5. 验证方法与剩余风险

- **CI 门槛**：push 后 arm64-v8a Release 编译通过。
- **真机清单**：
  1. 在「添加节点」页粘贴 vless/vmess/trojan/ss/hysteria2 链接并保存 → **不应有任何闪退**，
     且此时**不应有** sing-box 引擎启动日志（`SingBoxEngine`）；
  2. 返回代理列表页 → 出现"检测中"→ 得到"可用+Ping"或"不可用"（而不是恒"不可用"）；
  3. 节点行的 ping 值应当出现（说明引擎启动 + 域名解析 + 隧道均通）；
  4. 启用某节点后再次进入列表页 → 当前节点行显示 Ping，连接**不中断**，其它节点行不被误标；
  5. `adb logcat | grep -E "ProxyEngineClient|SingBoxEngine|LibboxEngine"` 观察是否仍出现
     `engine start timed out` / `engine process died`。
- **剩余风险与不确定处（如实记录）**：
  - 若真机仍闪退，从现象与现有证据看**最可能是 libbox 在原生层的崩溃**（Java 侧已无已知未捕获
    路径）。请提供 `adb logcat -b crash -d` 与 `logcat | grep -E "SingBoxEngine|LibboxEngine|DEBUG"`
    输出，我可定位到具体配置字段或具体调用。
  - 根因 C 的 DNS 解析器取 `223.5.5.5`：对**国内可解析**的节点域名有效；若某节点域名被国内
    DNS 污染，需要改用其他解析器（代码中 `BOOTSTRAP_DNS` 单点可改）。
  - `PlatformStub.localDNSTransport()` 仍返回 `null`，因此**不能**使用 `type:"local"` 系统解析；
    这是本方案的边界，不是遗漏。
